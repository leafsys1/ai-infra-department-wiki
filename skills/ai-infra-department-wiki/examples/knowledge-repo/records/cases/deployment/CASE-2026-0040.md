# 客户自理复现暴露的四类交付缺口：设备权限、镜像、权重与依赖

## Goal

交付物要能被「客户自理」复现：客户在一个陌生环境里，除 `run.sh` 之外不依赖交付方的任何东西——
不自建镜像、不共享本地权重池、不靠交付方口头说明。本案例记录一次批量客户自理化改造中**暴露并修复的
交付缺陷**，目标是把「跑不通」的报错逐条钉到具体缺口上，而不是笼统归因于「环境不对」。

## Baseline

- 交付包来自四个来源，合计 54 个 `run.sh`（自有交付目录 31、协作方交付 13、一次批量修复 7、额外小模型 3），
  转换清单逐条记录原文件 SHA-256。
- 这些包**在交付方本机是跑得通的**：自有交付目录的 31 个包每个都有 `DEPLOY.md` + `TEST_REPORT.md`，
  实测卡型 910B3；其中一个包另带一份跨机复现报告（`REPRO`，含 smoke/full 的退出码与产物 SHA-256）。
- 但本机跑得通靠的是一组隐式前提：本机已有自建镜像、本机已有权重池、宿主机的 CANN 环境变量已就绪、
  以及交付脚本里若干只有本机才成立的路径。

## Changed Variable

只改 `run.sh` 的**环境自理层**：镜像引用的解析、权重目录的定位与下载、容器内缺失依赖的补装、
CANN 环境变量的条件 source、设备权限与脚本自身的参数传递方式。模型权重、推理参数、镜像版本都不动。

## Controlled And Uncontrolled Variables

- 受控：镜像版本锁定为 `quay.io/ascend/vllm-ascend:v0.23.0`；模型权重与推理参数不变；单卡 910B3、TP=1。
- 受控：复现一律从**新建容器**执行（清洁环境门禁），不复用常驻容器。
- 未受控：不同来源交付包的内嵌写法差异很大（镜像名、路径、依赖各不相同），无法保证同类缺陷只有这几种。
- 未受控：宿主驱动版本（26.0.rc1）、网络条件（hf-mirror / ModelScope 可达性）、以及卡是否被其它容器占用。
- 未受控：并非 54 个包都有退出码记录——有实测证据的是其中若干包，见 Results。

## Procedure

1. **盘点建清单**：对全部 54 个 `run.sh` 逐条记录原文件 SHA-256，作为「改前身份」，避免改完说不清改了什么。
2. **设备权限与 CANN 环境**：新容器统一加 `--privileged --security-opt label=disable --network host`；
   容器内依次 source CANN 三件套（`ascend-toolkit`、`ascendnpu-ir`、`nnal/atb` 的 `set_env.sh`），
   文件不存在则不阻断。
3. **镜像自理**：识别自建镜像引用并替换为公共镜像；本地无该镜像时自动 `docker pull`，拉取失败即退出并提示网络。
4. **权重自理**：权重目录不存在或为空时，先回落到交付包内的 `models/` 子目录，再自动下载（详见 PAT-2026-0021）。
5. **依赖自理**：diffusers 类模型在容器内补装 `diffusers` 等依赖（优先国内 PyPI 镜像，失败回退官方源）。
6. **脚本纪律**：修掉空参数传参缺陷；生成后对全部产物执行 `bash -n` 全量门禁（不是抽查）。
7. **清洁环境复现**：在新建容器里跑 smoke 与 full 两轮，记录退出码、产物校验与验收脚本输出。

## Results

**脚本自身缺陷（修复前 7/7 全 FAIL）**：批量修复的 7 个模块，原脚本的收尾调用是
`python3 entry.py --model $SMOKE_ARG`；非 smoke 模式下该变量为空，命令行退化成 `--model` 后面无值，
argparse 报 `argument --model: expected one argument` 并以 **exit 2** 结束——这正是「上级团队一键
`./run.sh` 全 FAIL」的直接原因。修复后 7 个模块 smoke 与 full 两轮退出码均为 0。

**环境级缺口**：新容器内 `import torch_npu` 报 `aclInit, error code is 507899` +
`Resource_Busy(EL0005)`、`torch.npu.device_count()==0`，加 `--privileged` 后通过；CANN 三件套未 source
时报 `0x7020010`，补齐后通过。另有一次卡被其它容器占用导致同样的 507899，停掉占用容器即通过。

**镜像与权重缺口**：自建镜像引用在客户环境不可用（改为公共镜像 + 自动 `docker pull`）；权重默认路径写成
容器内路径（宿主机上不存在，导致挂载源无效）；权重目录为空时自动下载，hf-mirror 大文件走 XET 失败则
回退备用源。

**清洁环境复现记录**：round3 记录 2 个包跨目录清洁、全新容器 smoke+full 均 `RUN_EXIT=0`
（如 load=169.3s、gen=36.2s/16tok；full load=171.5s、gen=41.1s/64tok），验收脚本 `validate_delivery.py`
判 **PASS、0 errors、0 warnings**。另一个视频生成包在新机器复现 smoke/full 两命令均以 DONE 结束、
产物可解码、`GATE_RC=0`，且 smoke 产物 SHA-256 与开发运行逐字节一致。

## Conclusion

客户自理复现失败**不是模型或算子问题**，而是交付包对交付方环境的四类隐式依赖，加上一处交付脚本
自身的空参数缺陷。因果骨架是：交付方环境（有自建镜像、有权重池、CANN 已就绪、卡未被占用）
→ 换成陌生环境后这些前提全部不成立 → 逐项补齐（设备权限、CANN source、镜像替换/拉取、权重回落与下载、
依赖补装）→ 清洁环境退出码为 0、验收脚本 0 errors 0 warnings。

**边界**：结论只覆盖「容器化交付包 + 单卡 910B3」这一类交付形态；不是全部 54 个包都有退出码记录；
自动下载依赖外部源可达；未在客户真实机器上验证，只在本机的新建容器与另一台机器上复现过。

## Applicability And Risks

适用：任何以 `run.sh` 交付、由客户在陌生环境复现的 NPU 交付包；尤其是交付方与客户不共享镜像仓库、
不共享权重存储的场景。

风险：`--privileged` 放宽了容器的安全边界，必须在交付文档中显式说明并获得客户认可；自动下载引入网络
依赖（大权重下载耗时可能远大于推理本身）；自动替换镜像会改变客户实际运行的镜像，需在脚本输出中打印
替换前后的镜像名以便审计；`bash -n` 只能证明语法可解析，不能证明逻辑正确。
