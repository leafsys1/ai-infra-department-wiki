# 单一基础镜像 + 每模型最小文件的交付形态

## Goal

回答「万级模型怎么交付才不炸存储、又让客户能复现」这个问题：交付形态必须让**每个新模型的边际交付成本
接近零**，同时把「环境身份」这类容易漂移的东西固定下来。

## Baseline

- 目标规模是 1 万个 HuggingFace 模型在 910B 上「可用化」。
- 朴素做法是每个模型打一个镜像。按模型打包镜像后，镜像体积与版本数量随模型数线性增长，
  存储与拉取成本都扛不住；而且每个镜像都会成为一份需要单独维护的「环境身份」。
- 朴素做法之二是把权重一起打包进交付物，同样随模型数线性增长。

## Changed Variable

把交付物拆成「全局唯一 + 每模型最小」两层：全局层是基础镜像、通用 `run.sh`、通用验证与下载工具、
环境版本锁定文件；每模型层只放该模型变化的东西。

## Controlled And Uncontrolled Variables

- 受控：基础镜像唯一且版本锁定（`quay.io/ascend/vllm-ascend:v0.23.0`，镜像内 vLLM/vllm-ascend 0.23.0、
  torch_npu 2.10.0.post4、CANN 9.1）；卡型 910B3、单卡、TP=1。
- 受控：权重与镜像都不进交付包，只留「可执行的下载命令」。
- 未受控：本记录只读到公开仓的文档与实样文件，**未在本机复跑**；客户侧网络条件未受控。
- 未受控：`customer-deliverables/README.md` 正文写「每个模型 2 个文件」，而同文档目录树与验收输出
  列出 3 个（含 `bench_result.json`）。两处口径差异保留原样，本记录不作调和。

## Procedure

1. **全局层固定**：准备 1 份环境版本锁定文件（固件/驱动/镜像内组件版本）、1 份通用 `run.sh`、
   1 份通用验证脚本（可用性 + TTFT/TPOT）、1 份通用权重下载脚本、1 份架构判定脚本。
2. **每模型层最小化**：每个模型只写 `run_config.env`（卡/端口/TP/显存/精度等运行参数）+
   `model_metadata.yaml`（权重来源、适配动作、验证结果、可执行的复现步骤）；验收后再落 `bench_result.json`。
3. **权重不进包**：交付文档给出可复制的下载命令（hf-mirror + 关 XET），客户自己下载到宿主机目录。
4. **客户上新车流程**：拉一次基础镜像 → 下载权重 → 填 2 个配置 → `./run.sh` → 验证可用性 + TTFT/TPOT。
5. **保留三指针**：每条适配记录环境身份（镜像 tag + 组件版本）、权重身份（HF repo id + 分片清单）、
   验证结果（`bench_result.json` + 时戳）。
6. **不可变纪律**：正式 `bench_result.json` 一经创建不可变；修正只能新增文件或对非正式汇总补字段，
   不重写历史。

## Results

- 交付物结构：全局 5 个共享项（环境锁定文件、`run.sh`、验证脚本、下载脚本、架构判定脚本）+
  每模型 2~3 个文本文件；权重与镜像均不在交付包内。
- 客户复现步骤被压缩为：`docker pull` 基础镜像 → 下载权重 → 核对配置（端口、宿主机权重路径、指定卡）
  → `./run.sh` → `curl /v1/models` + bench 脚本。
- 示范模型 `Qwen/Qwen2.5-3B-Instruct` 实测：4/4 通过、TTFT 均值 78.2 ms、TPOT 均值 12.25 ms；
  `Qwen/Qwen3-1.7B`：5/5 通过、稳态 TTFT 均值 56.34 ms、TPOT 均值 9.565 ms、约 104.55 tok/s。
- 交付包内可直接读到三件套实样：`run_config.env`（含模型 ID、精度、TP/DP、显存利用率、最大长度等）、
  `model_metadata.yaml`（含权重下载命令、分片清单、适配动作、验证结果、7 步复现步骤）、
  `bench_result.json`（含 5 次运行明细、首个热启动请求的 TTFT 供参考）。

## Conclusion

万级模型交付的可行形态是「单一基础镜像 + 每模型最小文件」：镜像与权重都不进交付包，环境身份由锁定的
镜像 tag 与版本表固定，因此每模型只需交付少量文本文件，客户侧动作收敛为「填 2 个配置 + 下载权重 +
`./run.sh`」。因果骨架：模型数 N 增长 → 镜像/权重若按模型打包则成本随 N 线性增长且环境身份碎片化 →
改为全局层唯一、每模型层最小 → 边际交付成本与 N 解耦。

**边界**：该形态要求交付方与客户共享同一个可拉取的镜像仓库地址与稳定的镜像 tag；权重下载依赖外部源
可达；结论来自公开仓文档与实样文件，本记录未独立复跑。

## Applicability And Risks

适用：模型数量大、单模型改动小、客户只要能跑起来并看到 TTFT/TPOT 的批量交付场景。

风险：把环境身份全部压在一个镜像 tag 上，一旦该 tag 被覆盖或仓库不可达，所有模型同时不可复现——
所以版本锁定与「镜像不打补丁优先、必要才加 base-image 补丁」是硬前提；`run_config.env` 里的端口与
宿主机路径是客户侧最常改错的两处，交付文档必须明确标注；权重不入包意味着客户首次运行的等待时间主要由
下载带宽决定，而非模型加载。
