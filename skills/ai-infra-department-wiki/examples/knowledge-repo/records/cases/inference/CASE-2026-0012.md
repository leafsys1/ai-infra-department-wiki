# FlashComm1 DP2 严格 identity 布局下跳过 prefill 的大 tensor copy

## Goal

消掉冷 32K prefill 每个完整 chunk 里约 18.9 ms 的 `TensorMove`：在 DP2 行布局等长且无 slack 的 FlashComm1 场景下，识别出 all-gather 后的 unpad/reorder 与 reduce-scatter 前的 pad/restore 其实是严格 identity，命中时直接复用原 tensor。

## Baseline

- R0030 的 post-R0029 冷 32K profile 新显示这条链的 device copies 达到可测量量级：代表 chunk 为 `aclnnInplaceCopy...TensorMove` **306 calls / 18.869 ms**。
- full trace 的主要 shape：`[8096,4096]`、`[8096,256]`、`[2024,4096]`。
- full prefill 的 DP counts 相等，`padded_length=8096`，8096 可被 TP4 整除，每个 DP block 无 slack，因此 unpad/restore 严格为 identity。
- R0014 的 in-session counter 已观测每请求 `unpad_fused=86`、`pad_fused=43`，次数不随 decode 长度增长，正好对应每个 MoE 层的 prefill 入口覆盖。

## Changed Variable

- 文件：`framework/vllm-ascend/vllm_ascend/ops/register_custom_ops.py`。
- 新增 `_dp_layout_is_identity(total_rows, num_tokens_across_dp_cpu, dp_size)`，只有三个条件同时成立才命中：metadata 条目数等于 DP size 且非空；第一个及所有 rank 的 count 均等于 `_EXTRA_CTX.padded_length`；tensor 总行数等于 `dp_size * padded_length`。
- `_maybe_all_gather_and_maybe_unpad_impl` 直接返回 EP all-gather 输出；`_maybe_pad_and_reduce_impl` 直接把现有连续 tensor view 送入 EP reduce-scatter。
- 所有 ragged、slack、metadata mismatch、非 FlashComm1 / 非 EP 路径**保持原逻辑**。collective 数量与字节不变；减少的是 HBM copy、`TensorMove` launch、临时分配与 Python/dispatcher glue。
- 最终代码删除 A/B switch，只保留 strict identity fast-path。

## Controlled And Uncontrolled Variables

受控：同一冻结服务、同一 DP2×TP4/EP8 + DSpark K7 + FlashComm1 + DSA-CP + FULL_DECODE_ONLY + mlen 1M 配置，concurrency=1、temperature=0、max_tokens=8；每条 measured 请求前清 prefix cache，同一 prompt index 配对，偶数对 baseline→candidate、奇数对 candidate→baseline。

未受控：本轮**未跑 48×1024 正式吞吐**，主指标是 cold-32K TTFT；首对改善幅度偏大（8.249%），虽去掉首对后方向仍为 7/7 正，但已作为观测记录保留。

## Procedure

1. 复用 R0014/R0015 已建立的 strict predicate 语义验证：R0014 做 10/10 CPU + 10/10 NPU 的 identity/ragged/slack/1-D 等价检查，R0015 做 1350 个 CPU cases 与 100 个 NPU cases。
2. R0032 最终代码复用同一个 strict predicate，不带 S4 或探针逻辑；跑 `py_compile` 与 `git diff --check`。
3. 两轮同会话冷 32K A/B，每轮 4 对，逐请求 reset prefix cache 并断言 `success=true`、`prompt_tokens=32768`、`completion_tokens=8`、HTTP 成功。
4. 合并两轮计算配对中位与 sorted improvement，并检查去掉首对后的方向稳定性。

## Results

- 第一轮 TTFT 配对改善：`8.249% / 2.804% / 4.555% / 0.875%`，4/4 正向，中位 **3.679%**；总时长中位 3.509%。
- 第二轮 TTFT 配对改善：`1.041% / 4.026% / 1.559% / 4.402%`，4/4 正向，中位 **2.793%**；总时长中位 2.718%。
- 合并：**8/8 TTFT 正向**，sorted improvement `0.875, 1.041, 1.559, 2.804, 4.026, 4.402, 4.555, 8.249%`；TTFT 配对中位改善 **3.415%**，total-time 配对中位改善 **3.355%**。baseline TTFT 中位 **3.816009 s**、candidate **3.702958 s**；baseline range 3.757986–4.037970 s、candidate range 3.649574–3.732707 s。
- 首对幅度偏大，但去掉首对后方向仍为 **7/7 正**、配对中位仍约 2.8%，且两种臂顺序都成立，不依赖 cherry-pick。
- 正确性与协议：R0014 10/10 CPU + 10/10 NPU；R0015 1350 CPU cases、100 NPU cases，`FAILURES=0`（覆盖 identity、uniform-slack、ragged、零 token、D=1/256/4096 与多 dtype）；两轮所有 measured 请求均 reset `success=true`、prompt_tokens=32768、completion_tokens=8、HTTP 成功。

## Conclusion

在 FlashComm1 + DP2 且布局严格 identity 的 prefill 路径上，跳过 unpad/reorder 与 pad/restore 两处大 tensor copy 带来真实收益：两轮同会话共 8 对全部正向、TTFT 配对中位改善 **3.415%**、total-time 配对中位 **3.355%**，正确性与失败率不变，因此源轮次裁决 KEEP。

**3.4% 低于同机制族 5% 目标，但不是硬淘汰线。** R0014 已有同会话 decode 证据为 5/5 同向、decode period 中位仅 +0.40%，说明该变更不会以 TPOT 退化换 TTFT——只是 steady decode 覆盖少、收益小。命中门槛由 metadata 长度、每 rank count、`padded_length` 与 total_rows 共同证明 identity，ragged/slack 走原路径。

## Applicability And Risks

- 适用：FlashComm1 + DP2、每个 DP block 等长且无 slack 的 prefill 场景；collective 数量与字节不变，因此不需要改通信配置。
- 未覆盖（源里明确留白）：**未跑 48×1024 正式吞吐**；同会话 8 对两种顺序只验证了 prefill 收益，decode 侧收益仍以 R0014 的 0.40% 为准。
- 风险：布局一旦出现 ragged/slack，fast-path 不命中并回落到原逻辑——这是期望行为，不要为让收益变大而放宽 identity 判定。
- 风险：本记录是单实验室、单负载、单并行拓扑下的观测；`model_version` 与 `framework_version` 在源里没有给出，记为 unknown。
