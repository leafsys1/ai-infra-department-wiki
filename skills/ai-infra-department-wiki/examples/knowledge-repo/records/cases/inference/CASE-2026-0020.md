# Qwen3.8-27B W8A8 单 die 解码：每步 28.427 GB 权重读取已贴住 HBM 带宽上限

## 目标
回答一个问题：这套部署上单步解码到底卡在什么上——是算子没调好，还是别的物理上限？

## 基线
910C/A3 上一个逻辑 die（64 GiB），`TP1 · DP1`，Qwen3.8-27B W8A8（混合 FLOAT/W8A8_DYNAMIC）。
热解码路径按已归档的 graph trace 归账：每步 305 次 matmul family 调用，必须从显存读 **28.427 GB**
权重，matmul 设备时间合计 **23.765 ms**，等效 **1.196 TB/s**。其中仍有 5.61 GB/step（19.7%）是 bf16，
因为量化描述文件把 `linear_attn.out_proj.weight` 与 `lm_head.weight` 标为 FLOAT。

## 变更变量
本轮不改代码、不改权重、不改启动参数。被改的自变量只有一个：**请求并发档位**（1 / 2 / 4 / 8 / 16），
用来标定「单步已贴顶之后，吞吐还能从哪里拿」。带宽部分不是干预，是**定标测量**。

## 受控与非受控变量
受控：模型与量化口径、TP/DP 度、可见设备、启动 flags、prompt 集合（四条固定自然 128-token prompt）、
输出长度 32 token、temperature 0、seed 1024、`ignore_eos`、每档两遍同序重复、两端先做不计时预热。

未受控：宿主侧邻居负载与跨会话漂移（本轮未做跨会话对照）；并发 >1 时贪心输出的可复现性（见下），
因此本轮**不用逐字节 parity 做并发 A/B 的判据**。

## 执行步骤
1. 从八步窗口的 graph trace 恢复每个 matmul family 的 K/N，推算每次调用必读的权重字节，按解码步归一化。
2. 在**同一节点的一块空闲 die** 上跑独立带宽探针：只读 reduction、copy、以及占主导的 gate-up shape 的
   bf16 matmul（M=1 与 M=8 各一次）。
3. 把第 1 步的实测等效带宽与第 2 步的上限对照，判断是否还有可回收余量。
4. 并发标定：并发 1/2/4/8/16 同序各两遍，记录聚合吞吐、mean TTFT、mean TPOT、wall。
5. 护栏：全部请求必须恰好 32 个 completion token 与 128 个 prompt token；另检查跨并发的文本 parity。

## 结果
- **权重流量账目**（摘录 `S2-weight-traffic`）：total `305` 次调用 / `28.427` GB/step / `23.765` ms/step /
  `1.196` TB/s。逐 family 0.935–1.380 TB/s；最慢的是 `GDN in_proj_a/b`（K=5120、N=96）`0.074` TB/s。
- **同卡上限**（摘录 `S3-hbm-ceiling`）：只读 reduction `1.139` TB/s、copy `1.238` TB/s、
  M=1 bf16 matmul `1.037` TB/s，且该 matmul 在 M=8 时开销与 M=1 相同。
- **贴顶判定**：每个解码 family 都处在或高于实测可达带宽 ⇒ 这条路径上 kernel 选择、tiling、
  block-size 的改动**没有可回收余量**。
- **并发标定**（摘录 `S4-batch-scaling`，两遍数字）：并发 1 聚合 `27.98 / 28.09` tok/s、TPOT
  `29.87 / 29.85` ms；并发 16 聚合 `250.76 / 250.90` tok/s、TPOT `41.66 / 41.69` ms。
  固定预测「并发 16 相对并发 1 聚合 ≥8×」**成立**：`8.96×`；「每请求 TPOT 大致持平」只**部分成立**：
  每步成本 ×1.40，剔除 TTFT 后解码侧分摊为 11.4×。
- **噪声地板**：五档各测两遍、同序重复，**两遍在每个档位的差异 ≤0.5%**。
- **护栏**：全部 160 个计时请求都以恰好 32 completion token / 128 prompt token 成功；
  但预先注册的 **parity 护栏失败**——temperature 0 + 固定 seed 下，同一条 prompt 在 4 条中有 3 条
  于不同并发级别间产生不同文本，甚至有 2/4 条在同一并发的两遍之间也不同。

## 结论
在 910C/A3 单逻辑 die、TP1、Qwen3.8-27B W8A8 这个部署点上，**热解码路径受单 die HBM 带宽约束，
算子已贴在物理上限上**：每步必须读的 28.427 GB 权重只能以约 1.196 TB/s 的速度读完，与同卡实测上限
同量级（读 1.139 / 拷贝 1.238 / M=1 bf16 1.037 TB/s）。因此在这条路径上继续压单步**拿不到收益**，
剩下的杠杆是更少的权重字节、更多的 die，或每次权重读取摊到更多 token——本轮实测后者可用：
并发 1→16 聚合吞吐 ×8.96，代价是每步成本 ×1.40。

**边界与未覆盖项**：并发高于 16、长上下文与 prefill 主导的负载、prefix caching、TP > 1、通信主导的
区间，以及任何跨架构结论**均未覆盖**；这是单一部署点上的机制刻画，不是验收结果。通用模型精度仍为
**UNVERIFIED**。上游另给出证伪条件：若未来在本部署某个 arm 上测到 matmul-family 速率高于大致
1.25–1.4 TB/s，则本轮关于「余量已尽」的结论即为错误，应重启 kernel 层面的工作。

## 适用范围与风险
适用于「单卡单实例、热解码、权重读取主导」的工作负载。风险两条：一是**并发换吞吐不是免费的**，
每步成本会涨（×1.40）；二是**并发 >1 时贪心输出不可复现**（parity 护栏失败），所以并发 A/B 不能
用逐字节输出一致作判据，否则会误判。不要把这轮的「贴顶」外推到 prefill 或长上下文。
