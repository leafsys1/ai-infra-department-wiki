# R0038 DSpark copy-and-expand grid-stride：单算子 5.55–6.07× 但冻结同会话 4 对吞吐全部负向 → REVERT

## Goal

判断把 DSpark 的 copy-and-expand 步骤改成 grid-stride 并行能否在端到端服务上成立：单算子收益
看起来很大，问题是它能否支配完整 decode period。

## Baseline

生产模块中未改动的原 kernel。模型为 DeepSeek-V4-Flash W4A8，平台 910B3。判定负载为
`max_model_len=1048576`、DP2×TP4/EP8、DSpark K7 eager、FlashComm1、DSA-CP、c12、32K 输入、max256，
4 对交替顺序（配置原文见摘录 §配置，来源 `evidence/RUN.md`）。

## Changed Variable

一个候选 kernel 实现：把 copy-and-expand 由原实现改为 grid-stride 并行（三个候选文件）。原函数
完全不动、候选独立追加，其余启动参数与负载不变。

## Controlled And Uncontrolled Variables

受控：同一会话、同一拓扑、同一 checkpoint、同一冻结负载与启动参数；A/B 交替顺序（4 对，双向）。
未受控：候选带来的额外并行 launch 成本——它在 decode 小 shape 上本身约慢 0.8–1.2%，这部分成本会
被带入更多 decode iteration，而本轮未单独定价。

## Procedure

1. 先在**生产模块**里做最小单算子验证：原 kernel 与候选 kernel 直接 A/B，6 组 shape 的 6 类输出
   全部 `torch.equal`，同时记录 event 与 wall 耗时。
2. 再在冻结 1M 同会话 c12 配置上做 4 对交替 A/B，看完整 TPOT、TTFT 与 output throughput。
3. 判定条件：需要"稳定真实下降"才 KEEP。

## Results

- 单算子（8K 级 context，生产模块，6 组 shape 输出 bit-exact）：B=6/context=8190 event
  1112.42→183.13 µs（6.07×）、wall 1123.78→195.83 µs（5.74×）；B=12/context=8184 event
  1115.59→201.01 µs（5.55×）、wall 1126.46→212.52 µs（5.30×）；B=6 mixed/context=3856 event
  534.52→222.24 µs（2.41×）；B=1/6/12 decode 小 shape 候选**约慢 0.8–1.2%**。
- 冻结同会话 A/B（4 对）：TPOT 改善 −18.81% / +8.18% / −23.82% / +2.56%，**中位 −8.12%**；
  output throughput 改善 −28.14% / −1.01% / −10.73% / −0.10%，**中位 −5.87%**；TTFT 中位 −0.63%。
  原始 JSON `summary`：`tpot.median_pct = -8.124736437317017`、`tpot.positive_pairs = 2`、
  `throughput.median_pct = -5.87014968898046`、`throughput.positive_pairs = 0`、`all_valid = true`、
  `all_first_text_equal_by_request = true`。
- 有效性与一致性：全部请求满足 32768/32770 prompt token、256 completion token，所有 baseline/
  candidate 首块文本逐请求一致。
- 回退：三个候选文件已恢复到 R0038 前快照，`git status` 仅保留 R0017/R0020/R0029/R0032 的既有
  KEEP 修改；服务已停止。

## Conclusion

**没过的闸**：KEEP 条件要求"稳定真实下降"。实际 TPOT 仅 2/4 正向、吞吐 **0/4 正向**（中位
−5.87%），配对方向不稳定，因此 REVERT。机制解释（原文）：该 kernel 对每个 proposal 只回收长
context 时约 0.9 ms，完整 period 仍由更大的 attention/MoE/通信与调度决定；进入 steady decode 后
context 小，候选自身又约慢 1%。所以局部收益既不足以支配完整 TPOT，也可能把 launch 成本带入更多
decode iteration。

**未覆盖项**：① 未跑正式 48×1024；② 一次诊断补丁误把旧 kernel 定义插入候选函数中部，导致服务首
请求 MTE 越界（该服务立即停止、补丁废弃），未把该失败算作候选正确性证据；③ 一次 A/B 误用启动脚本
默认 `max_model_len=133072`，其 TPOT 中位也为负，但不符合冻结 1M 配置，**不纳入正式判定**——权威
结果仅为 mlen1M 文件。

## Applicability And Risks

适用于"单算子 microbench 收益很大、但端到端未必成立"这一类判断，尤其是长 context 才显现的算子。
**不适用**：不能把 6× microbench 等价成端到端收益；上游在相似配置上的大幅报告也不能替代当前冻结
路径的 A/B。这条 grid-stride 单点不应重开；若未来与更大的同机制 input-preparation fused op 合并，
必须重新计算完整族的可回收量，并继续以真实 TPOT/decode period 判定。
