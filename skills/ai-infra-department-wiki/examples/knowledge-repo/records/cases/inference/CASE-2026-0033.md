# R0056 两条零卡静态否证：本引擎无 multi-step 旋钮 / 补齐 decode 图捕获覆盖 248→256 无收益对象

## 目标
在**不占用 NPU、不起停服务、不做性能测量**的前提下，先用静态取证判定两个候选"有没有收益对象"：
① 是否存在 multi-step scheduling 旋钮；② 补齐 decode 图捕获覆盖（248→256）是否值得做。若不存在收益
对象则直接否证，不必起服。

## 基线
本条合并归档两个主体，部署不同，判据相同（先判存在性/收益对象，再决定是否起服）：
- 主体 A：`qwen38-27b-w8a8`；910C 单机 16 die，**双实例**（组 A / 组 B 各占一组物理 die，各 `TP4`）；
  现场 `max_model_len 36864`、`--max-num-batched-tokens 8192`、`--max-num-seqs 8`、
  `--gpu-memory-utilization 0.80`（两组同形）。
- 主体 B：`deepseek-v4-flash-w8a8`；910C 单机 16 die，**单实例不分 P/D**（`DP16 · TP1 · EP16`）；
  现场 `--gpu-memory-utilization 0.88`、`--max-model-len 262144`、`--max-num-seqs 32`、
  `--block-size 32`、`cudagraph_mode=FULL_DECODE_ONLY`、speculative **已禁用**。

frontmatter 的 `topology` 记主体 B 的形态。Base Stack（原文）：容器镜像
`quay.io/ascend/vllm-ascend:nightly-releases-v0.26.0rc-a3`；引擎 **vLLM 0.26.0**（python 3.12.13）；
vLLM 源码快照 `568afb3a13806beb53bb2e6bd518269357b237c0`；vllm-ascend 源码快照
`31b1176a4226968f28c4bb6e04bb1a36636ed38d`。

## 变更变量
两个候选，本轮都**不改代码**：
- 主体 A 的候选是"打开 multi-step scheduling 以减少每 token 的 host 控制路径空洞"（拟用旋钮）。
- 主体 B 的候选是"把图捕获上限由 248 补齐到 256"。图捕获上限保持 **248**、捕获清单保持
  `[8,16,…,248]`（31 项，步长 8）——即**实际未改动**。

## 受控与非受控变量
受控：同一容器镜像与同一引擎版本；只读取证不改任何文件、不改权重、不改参数。
未受控：主体 B 未覆盖 `max_num_seqs=32` 满载；桶边界无法分辨 `(248,256]` 窄带；主体 B 的
`arm_R_*` 桶表对照与逐 rank 桶分布汇总**未取得（MISSING）**，本轮不补算。主体 A 原轮状态为
`BLOCKED`（未进入 A/B）。

## 执行步骤
主体 A —— 容器内四层只读取证，零 NPU、零起停：
1. `vllm serve --help=all` 全量导出（116907 B / 1826 行）后用同族模式匹配；
2. `inspect` 出 `SchedulerConfig` 的字段全表；
3. 用引擎自带的 `make_arg_parser` 做真实解析探针；
4. 容器全域 `grep -r num_scheduler_steps`、`vllm/v1/core/` 内 `grep -E 'multi_step|num_steps|n_steps'`、
   全树 `grep -rE 'multi_step|MultiStep'`；另做运行中实例 argv 的前后一致性核验。

主体 B —— 四份迭代桶表快照复算：对 `(128,256]`、`(256,2048]`、`(2048,4096]` 三个区间求增量，并与
累计请求条数逐单元对照。

`validation.repetitions` 记 **4** 的语义：主体 A 为四层**独立只读取证通道**，主体 B 为四份**独立桶表
快照**复算——是独立证据条数，不是同一测量的重复采样。

## 结果
主体 A（逐条）：
- `--help=all` 同族模式命中 **0 行**（落盘文件 0 字节）；默认 `--help` 只列 88 行 Config Groups，故以
  `--help=all` 为准。
- `SchedulerConfig` 字段全表**回显 20 行**，不含 `num_scheduler_steps`（**原样保留的口径差异**：来源
  结果文件记为「21 个字段」而原始回显打印 20 行，两者并原样保留、不自行裁齐；结论不受影响）。
- 真实 argparse 探针对三种写法一律 `error: unrecognized arguments`、**rc=2**。
- 容器全域 `grep num_scheduler_steps` **0 命中**；`vllm/v1/core/` 内三关键词 **0 命中**；v0 引擎目录
  `vllm/worker/` **不存在**。
- 全树 `multi_step|MultiStep` 仅 **5 行**且均无关（3 行 `template_minicpmv45.jinja` 模板变量 + 2 行
  `spec_decode/autoregressive/speculator.py` 的 `_multi_step_decode`，属投机解码内部一次验证多步草稿）。
- 本版本 `async_scheduling` **默认 True**（`vllm/config/vllm.py:1101-1112` 的 `else` 分支；运行中实例
  日志可证 `Asynchronous scheduling is enabled.`）；轮次开始与结束两次 argv 回显**逐字一致**。

主体 B（逐条）：
- 四份快照 `(128,256]` 增量 **0 / 0 / 0 / 0**；`(256,2048]` 区间迭代数 **0 / 0 / 0 / 0**
  （`le=512/1024/2048` 恒等于 `le=256`）。
- `(2048,4096]` 累计迭代数 **1 / 2 / 3 / 1**，与该臂运行到该单元的**累计请求条数** 1 / 2 / 3 / 1
  一一对应 ⇒ 3072-token prompt 的**整段 admission（prefill 步）**，不是 decode 步。
- 各单元 `count`/`sum` = 25/3200、46/6400、66/9600、18/2176；**所有 decode 迭代 ≤128 token**，
  无任何逼近 248 的 decode 迭代 ⇒ **无 >248 的 decode 迭代**。
- 告警 `248 < 256` 命中 **16 个 rank 各 1 次**（`TOTAL_OCCURRENCES=16`），为**一次性启动告警**；
  告警里的 `256` = `max_num_seqs(32) × (num_speculative_tokens(7)+1)` 的**理论潜力**，而现役**已禁
  speculative** ⇒ 该潜力**不可达**。

## 结论
主体 A —— **REVERT**（`status: BLOCKED` 的原轮口径不变：前置门禁不通过，未进入任何 A/B、无任何臂、
无任何性能测量）。**没过的闸**是存在性前置门禁：本版本/本路径下 multi-step scheduling **无同名
旋钮**；"减少每 token host 控制路径空洞"的既有承担者是**默认已开**的 async scheduling。**不产出 OPT。**

主体 B —— **REVERT**（零卡静态否证：无收益对象，不必起服、不必压测）。**没过的闸**是"存在落在缺口
区间的迭代"这一判据：缺口区间增量为 0，告警里的 256 只是不可达的理论潜力。同时**撤销**该候选原有
"改判（补齐 256）"的前提。

**可复用判据**：登记「**是否存在落在缺口区间的迭代**」可零卡判定覆盖/形状类候选，无需起服。

**未验证项（原样保留）**：主体 A 原轮状态为 `BLOCKED`（未进入 A/B）；主体 B 未覆盖
`max_num_seqs=32` 满载、桶边界无法分辨 `(248,256]` 窄带；主体 B 的 `arm_R_*` 桶表对照与逐 rank 桶
分布汇总未取得（MISSING），本轮不补算。性能验收状态：**本轮无性能测量**（两条均为静态/存在性否证，
不含收益量级；既不声称为收益，也不声称某旋钮有害）。

## 适用范围与风险
适用于任何"先判有没有收益对象/有没有这个旋钮"的候选：这类否证**零卡可做**，成本远低于起服压测，应
作为前置门禁。**不适用**：不能把"本版本没有该旋钮"外推到其它版本（换版本须重新核对字段与行号）；
不能把"桶计数为 1"解释成"只发生了一次分块 prefill 步"。风险点：口径差异（20 行 vs 21 个字段）应
原样保留而不是自行裁齐；主体 B 的窄带分辨力不足，若未来要判 `(248,256]` 内是否有迭代，需要更细的
桶边界。
