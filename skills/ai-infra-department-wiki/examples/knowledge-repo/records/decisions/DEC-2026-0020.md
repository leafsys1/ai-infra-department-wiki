# 交付验收标准：客户在陌生环境仅凭交付物即可复现

## Decision

交付物的验收判据是：**客户在一个陌生环境里，除 `run.sh` 之外不依赖交付方的任何东西**。
具体地说，交付物不得要求客户：使用交付方的自建镜像、访问交付方的本地权重池、安装交付方的私有
Skill 或脚本、或自行补上一个文档里没写的依赖。

判据的检查方式是「复现演习」：在清洁环境（新建容器、无自建镜像、无本地权重池）只按交付文档操作，
以 `run.sh` 的退出码与验收脚本输出作为判定依据。任一环节要求交付方资源，即判不通过。

## Rationale

- **交付物跑不起来等于没有交付**：客户侧的失败成本远高于交付方内部的一次「在我这儿是好的」。
- 竞争性项目是按**复现成本与复现成功率**选型的：同样能跑的两个交付物，客户会选那个不需要反复来回
  问人、不需要改环境就能跑起来的。降低复现成本本身就是竞争力。
- 复现失败的原因往往不在模型与算子，而在交付包对交付方环境的隐式依赖。这类依赖在交付方内部
  完全看不出来——本机已有镜像、已有权重池、环境变量已就绪，所以必须换到陌生环境才暴露。
- 判据要能被机器检查：退出码、验收脚本的 errors/warnings 计数、镜像 tag 一致性，都是可复算的量；
  而「应该能跑」不是判据。

## Supporting Evidence

- CASE-2026-0040：54 个交付包在陌生环境复现时，失败全部集中在四类自理缺口（设备权限与 CANN 环境、
  自建镜像引用、内部权重路径、容器内缺失依赖），另有一处空参数脚本缺陷使一键复现 7/7 全 FAIL；
  逐项补齐后清洁环境退出码为 0、验收脚本 0 errors / 0 warnings。
- CASE-2026-0041：单一基础镜像 + 每模型最小文件的交付形态，把「环境身份」固定在锁定的镜像 tag 上，
  权重与镜像都不进交付包，客户侧动作收敛为「填 2 个配置 + 下载权重 + `./run.sh`」。
- CASE-2026-0042：三个架构家族走同一六步流水线、零代码改动，验收口径为「可用 + 稳态 TTFT/TPOT」，
  且明确「复现演习必须真实跑，不能只相信能跑」。
- 公开仓验收文档的硬约束与本判据同向：**最小化存储**（不复制权重、不复制镜像到模型目录）、
  **可复现**（`reproduce_steps` 每步都必须是可直接执行的命令）、**绝不改权重**、`available` 必须为 true
  才 PASS，以及**复现演习必须真实跑**（不能只「相信能跑」）；其验收流程第 6 步就是「干净容器跑一遍
  run.sh + bench，证明按文档能复现」。

## Counter Evidence

- 「客户自理」不等于「零配合」：客户仍需提供卡、驱动、网络与一个可写的权重目录。把这些算作
  「依赖交付方」是误判；本决策只约束交付方资源。
- 存在合理的例外：涉密或强隔离环境下客户明确要求使用其自有镜像与内网权重源时，交付物按客户镜像适配，
  此时「不依赖自建镜像」退化为「依赖客户镜像」，判据变成「镜像由客户指定且 tag 可核验」。
- 清洁环境复现并不能证明逻辑正确：`bash -n` 只证明语法可解析，冒烟通过也只覆盖默认参数路径。
- 本决策的三条支撑案例中，只有 CASE-2026-0040 有本机退出码记录；CASE-2026-0041/0042 只读到文档与实样
  文件，未独立复跑。

## Applicability

适用：以 `run.sh`（或等价的单入口脚本）交付、由客户在自有环境复现的 NPU 交付包；批量模型交付场景下
尤其必要，因为客户不会为每个模型来回确认环境。

不适用：客户明确指定运行环境与镜像的定制项目；交付物本身就是镜像或算子库、而非可执行交付包的情况。

## Revisit Conditions

- 客户侧开始提供统一的镜像仓库与权重源，使「自建镜像」不再是客户不可达项。
- 出现「客户自理」成本高于其收益的场景（例如客户要求深度定制镜像）。
- 复现演习出现稳定的假阴性/假阳性（例如网络波动导致权重下载失败被误判为交付缺陷），需要调整判据。
