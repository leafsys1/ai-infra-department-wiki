# 重写面向人的页面，必须对照文档承诺的能力清单逐条验证

## 触发信号
一个面向人的页面被重写或替换后，功能看起来更好，但文档里写明的某条能力在页面上找不到入口；
渲染类断言全绿，测试没有任何失败。

## 根因
重写者以“新设计”为目标，按自己的理解重建页面。文档里承诺的能力——回退通路、安全约束、入口——
不在新设计里，删掉时不会触发任何测试：既有断言检查的是渲染结果（条数、计数、能否点开），不是
能力清单。于是“测试全绿”与“能力被删”可以同时成立。

## 处理模式
动手改页面之前，先从文档里把承诺逐条列出来（读 SKILL.md / README 中描述该页面行为的那一节），
再在新页面里逐条验证：

- 每个文档提到的**入口**在页面上存在且可用（本次实例：`file://` 下“导入 catalog.json”的手动通路）；
- 每个文档提到的**安全约束**仍在代码里（本次实例：来源 URL 只允许 http/https/mailto，且不得插进
  `href`）；
- 每个文档提到的**数据来源**仍被读取（本次实例：关系来自 `graph-data.json`）。

任何一条缺失，要么补回实现，要么同步改文档——不能靠删掉断言让测试变绿。

## 前置条件
页面行为被写进文档（README / SKILL.md / 参考文档），并且存在针对该页面的自动断言。

## 不适用场景
纯视觉或排版重写、且文档未承诺相应能力时，本条不适用。反之，若文档承诺了而实现没有，那是文档
缺陷，同样要处理，只是处理方式改为改文档。

## 最小验证
重写后逐条比对文档承诺与页面实现，并把其中可自动化的条目写成断言：入口存在、安全约束仍在、
数据来源仍在。

## 支持案例
`CASE-2026-0004`（看板分发与 HTTP 通路）、`CASE-2026-0005`（字段契约与静默降级）。

## 反例
若文档写的是愿景而非承诺（例如“未来支持”），缺失不算缺陷。判断依据是：文档是否把它写成用户可以
照着执行的步骤。
