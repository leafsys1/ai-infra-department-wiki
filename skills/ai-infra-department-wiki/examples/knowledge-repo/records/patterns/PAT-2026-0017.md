# host 下发/胶水常常比设备算子本身更贵：先量 host:device 比例

## Trigger Signals

一个段在 profile 里很贵，但设备侧算子工作量看起来很小。

讨论里把「段耗时」直接当成「算子耗时」。

## Root Cause

每层、每迭代有大量叶子 host op（metadata builder、格式转换、胶水），下发开销累积；设备算子只占小部分。比例不量出来，优化对象就会选错。

## Action Pattern

1. 同一段同时给 host 侧与 device 侧计时，算出 host:device 比例。
2. 比例悬殊时优先看 host 侧：下发次数、胶水、格式转换。
3. 再算上界并与闸门比较（PAT-2026-0010）；比例高不等于值得动。

实例：

- R0011：draft MoE 15.268 ms/22.24% 里 host 下发与胶水 7511 µs/层（折算 22533 µs/迭代 = 25.5% of period），对应设备工作量仅约 205 µs/层 = 0.70% of period，host:device 约 36:1；每次调用 85 个叶子 host op。
- R0012：qkv 段 1529.2 µs/层 = op 758.0 加 host glue 769.5，host:device 约 29:1。
- R0013：每迭代 8 次 metadata builder 均匀铺出的 host 下发马赛克，区域内 413 个 host op、16.89% of period；最大单族上界 4.72%，低于 5% 门槛。

## Preconditions

有 host 与 device 两侧时间分解的 profile，或可离线复用的既有 trace。

## When Not To Apply

设备算子本身占主导时（大 GEMM 类）比例不悬殊，优化对象就是算子。

host 开销大但上界低于闸门时也不该动（R0013 的 4.72%）。

## Minimum Validation

同一段给两侧计时并算出比例，再给出上界与闸门的比较。

比例、上界两个数字都要有，缺一个就不能立项。

## Supporting Cases

- R0011：host:device 约 36:1，每次调用 85 个叶子 host op。
- R0012：host:device 约 29:1，1529.2 = 758.0 加 769.5 µs/层。
- R0013：413 个 host op，最大单族上界 4.72%，低于 5%。

## Counterexamples

R0013 的比例很高，但最大单族上界 4.72% 仍低于 5% 门槛，被合同排除：说明「host 更贵」只决定优化对象在哪，不决定该不该做。

R0012 里 qkv 整段只占 5.50% of period，单点候选需去掉整段 90.9%，算术上不可达。
